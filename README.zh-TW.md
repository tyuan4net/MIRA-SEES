# MIRA Spacetime Expression and Exchange Standard（MIRA-SEES）

> 一套讓人能手寫、彼此能討論、程式也能解析與計算的時空表達語言。

**狀態：Draft — 公開討論與實作驗證中**

MIRA-SEES 嘗試解決一個看似簡單、實際上經常造成錯誤的問題：

> 當我們寫下一個日期、時間與地點時，這些數字究竟表示哪一種時間？又附帶了多少地理資訊？

「1960 年 6 月 28 日 14:45」可能是出生證明上的當地鐘錶時間、排除夏令時間後的地方標準時間、UTC、地方平太陽時，或地方真太陽時。若交換資料時只留下數字，時區規則、DST、經度、均時差與原始語意很容易在轉換過程中消失。

MIRA-SEES 為這些差異提供一組簡短、醒目而可解析的表達方式，使同一份時空資料可以在人與人、人與程式，以及不同計算系統之間交換。

## 為什麼需要它？

許多時空錯誤並不是演算法不夠精確，而是輸入資料沒有說清楚。

例如：

- 出生證明記錄的是當時牆上時鐘顯示的行政時間；
- 天文計算通常需要先得到唯一的 UTC 瞬間；
- 宮位、ASC、MC 等計算還需要實際經緯度；
- 某些八字、紫微或其他傳統系統的流派可能採用地方平太陽時或地方真太陽時；
- 歷史地方時間、夏令時間與行政時區規則會隨地區及年代改變；
- 未來的行政時區規則可能尚未決定，不能取代已知的 UTC 事件時間。

如果這些語意沒有被保存，兩套各自「算對」的程式仍可能得到不同答案，而且很難查出差異從哪裡開始。

MIRA-SEES 的目標不是發明新的時間制度，而是把原本隱藏在上下文裡的假設明確寫出來。

## 從一組出生資訊，建立可交換的人生圖譜資料

MIRA 的預計範圍不只包含單一排盤系統。Human Design、西洋古典占星、印度占星／Jyotish、八字、紫微斗數、凱西占星（Cayce Astrology）與榮格占星（Jungian Astrology）等系統，未來都可以使用同一組已正規化、可追溯的出生時空資料，再產生各自的結構化結果。

```text
一組原始出生資訊
        │
        ▼
MIRA-SEES 時空 normalization
        │
        ├──► Human Design 結構化資料
        ├──► 西洋／古典占星結構化資料
        ├──► 印度占星／Jyotish 結構化資料
        ├──► 八字、紫微結構化資料
        ├──► 凱西占星結構化資料
        └──► 榮格占星結構化資料
                      │
                      ▼
        與人生事件、觀察、標籤及關係連結
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
        人類解讀     AI 協作     第三方程式分析
```

這些輸出不應只是一次性報表或只能觀看的圖片。它們可以成為有欄位定義、來源、版本與計算條件的資料，讓不同作者、不同程式與不同年代的工具能夠解析和交換。

出生時空是各系統共用的錨點；每套系統的計算結果、術語與規則則保留自己的 schema 與 provenance。MIRA-SEES 不把不同命理體系混成同一套規則，而是先確保它們談論的是哪一個時間、哪一個地點，以及資料如何從原始紀錄被轉換而來。

當結構化的命理資料再與實際人生事件並置後，人或 AI 可以進行跨系統比較、尋找對應、提出解釋或檢驗假設。其他人撰寫的程式也能加入同一資料交換環境，而不必先猜測 MIRA 私有的時間與地點慣例。

計算資料與解釋仍是不同層次：同一份可重現的結構化結果，可以有不同流派、不同作者或不同 AI 的解讀，而不必重新改寫底層出生資料。

## 核心概念

MIRA-SEES 將一筆時空表達拆成兩類資訊：

1. **目前使用哪一種時間表示**；
2. **這筆資料附帶或採用哪一類地理資訊**。

### 時間表示碼

| 代碼 | 意義 | 常見用途 |
| --- | --- | --- |
| `I` | IANA 當地行政時間 | 出生證明、牆上時鐘、一般 local time |
| `IS` | 排除 DST 的地方標準時間 | 比較、研究或明確不採季節撥時的情境 |
| `U` | UTC 唯一瞬間 | 跨系統交換、天文核心、timeline、return |
| `LM` | Local Mean Time，地方平太陽時 | 歷史 LMT 或指定經度的平太陽時 |
| `LS` | Local Solar Time，地方真太陽時 | 明確採用經度與 EOT 的計算方法 |

### 地理資訊碼

| 代碼 | 意義 | 回答的問題 |
| --- | --- | --- |
| `A` | IANA timezone 層級，預設可省略 | 使用哪一套行政時間規則？ |
| `B` | Local 行政地區 | 人所說的城市、鄉鎮或地區是哪裡？ |
| `C` | 明確經緯度 | 實際計算使用哪個地球位置？ |
| `D` | LMT 參考經度 | 歷史鐘錶依哪條參考經度解讀？ |

`D` 不是比 `C` 更高的定位精度，而是另一種用途的資料：實際事件地點與歷史鐘錶採用的參考經度可能不同，兩者不應混在同一欄位。

## 人可以寫，程式也可以讀

文件、報表或討論中可以使用醒目的寫法：

```text
I<1990.3.20.8.30>
IB<1990.3.20.8.30>
IC<1960.6.28.14.45>
U<1960-06-28T05:45:00Z>
LMD<1870.5.10.8.20>
LSC<1960.6.28.14.43.20>
```

例如，`IC<1960.6.28.14.45>` 表示這是 IANA 當地行政時間，而且附有明確經緯度。完整資料仍會一併保存必要欄位：

```text
Birth spacetime: IC
Local time:        1960-06-28 14:45:00
IANA timezone:     Asia/Taipei
Resolved offset:   UTC+09:00
UTC:               1960-06-28T05:45:00Z
Area:              台灣／台北市
Place:             台北市郵政醫院
Coordinates:       25.0288072263 N, 121.5189180277 E
```

前綴不是完整資料的替代品。它是簡短的語意標記，讓人一眼知道目前談的是哪一種時間、資料帶到哪一層地理資訊；必要的 timezone、座標、offset、演算法與版本仍由欄位或結構化資料保存。

在 CLI 中，為避免 `<`、`>` 被 shell 當成特殊字元，可以改用：

```text
IC:1960.6.28.14.45
```

或把語意與數值分開：

```text
--time-style IC --time 1960.6.28.14.45 \
  --tz Asia/Taipei \
  --lat 25.0288072263 \
  --lon 121.5189180277
```

## Normalization：保留原始語意，再建立共同計算值

```text
[ 手寫紀錄／出生證明／手機／其他軟體 ]
                       │
                       ▼
          [ 辨識時間表示與地理資訊 ]
                       │
                       ▼
      [ 解析 offset、UTC 與可重現 metadata ]
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
   天文／HD 核心   宮位與四角    太陽時間系統
       UTC/JD       UTC + C      LM／LS + EOT
```

Normalization 不應抹掉原始資料。它應同時保留：

- 原始地方日期時間及其表示類型；
- IANA timezone；
- 已解析的 UTC offset 與 UTC；
- 行政地區、地點及經緯度（若有）；
- DST 重複時間的實際選擇；
- 使用的 tz database、EOT 或其他演算法版本（需要重現時）。

因此，不同系統可以共用同一個 UTC 計算層，同時仍能知道原始資料是怎麼被理解的。

## 不無聲猜測

MIRA-SEES 希望讓模糊處可見，而不是用預設值悄悄掩蓋它。

- DST 秋季回撥時，一個 local time 可能對應兩個 UTC；系統必須要求選擇或保存已知 offset。
- DST 春季跳時中，有些 local time 根本不存在；系統應拒絕或要求修正。
- 行政地區名稱不等於 IANA timezone，也不保證能自動推定唯一時區。
- `B` 表示知道行政地區，不假裝知道精確 GPS。
- `C` 表示有明確座標，但座標來源與不確定度仍可另外保存。
- 未來地方行政時間可能因規則變更而改變；長期事件應以 UTC 保存 canonical instant。

「無歧義」不是指一個短前綴能憑空補齊所有資料，而是完整 payload 必須暴露歧義、拒絕無聲猜測，並保存足以重現轉換的資訊。

## 跨系統使用

### Human Design

```text
IC local birth record
→ normalization
→ U
→ existing UTC calculation core
```

Human Design 核心不必因新增 local input 而重寫。

### 西洋占星

```text
IC
→ UTC／astronomical time + latitude + longitude
→ planets, points, ASC, MC and houses
```

星體位置與宮位所需要的資料不同；MIRA-SEES 使這個差異可以明確表達。

### 八字、紫微與其他傳統系統

```text
IC original record
→ U
→ longitude-based mean solar time
→ optional EOT
→ LM or LS calculation profile
```

是否採用地方平太陽時、地方真太陽時，以及採用哪一種演算法，取決於實際系統或流派。MIRA-SEES 不替流派作決定，而是讓所採用的規則可以被標明、交換與重現。

### Timeline、transit 與 return

長期天文事件首先保存為 UTC 唯一瞬間：

```text
U<2078-03-04T06:13:22Z>
```

顯示時再依需要投影為某地的 `I`、`IS`、`LM` 或 `LS`。這可避免未來 timezone 或 DST 規則改變後，事件本身也跟著漂移。

### 凱西占星與榮格占星

凱西占星與榮格占星將作為 MIRA 未來的資料輸出與研究層。它們可以共用 MIRA-SEES 正規化後的出生時空與底層天文資料，但各自的概念、對應規則、來源與版本仍應由獨立 schema 表達。

如此一來，後續研究可以引用同一份出生資料與天文計算結果，並清楚區分：哪些是可重現的計算值、哪些是特定體系建立的結構、哪些又是人或 AI 所提出的解釋。

## 設計原則

1. **人機雙適**：適合手寫、交談與報表，也能映射到 CLI、JSON、API 與資料庫。
2. **語意與數值分離**：時間怎麼寫，和它代表哪一種時間，是兩件不同的事。
3. **原始資料與衍生值並存**：Normalization 建立共同計算值，但不覆蓋來源。
4. **模糊性必須可見**：缺少資料、重複時間、不存在時間與推定值都不可無聲處理。
5. **漸進實作**：每個程式只需實作自己宣告的子集合，不必一次支援所有表示。
6. **可重現**：會影響結果的 timezone database、time scale、EOT 或其他演算法應能被記錄。

## 目前狀態

MIRA-SEES 現在是一份待實作驗證的公開草案，不是已完成或經標準組織核准的國際標準。

目前優先以真實使用情境驗證：

1. Human Design 的 `I`／`IB`／`IC` local input；
2. `planet_dump` 的 `U` 計算介面；
3. 八字、紫微等系統對 `LM`／`LS`、經度及 EOT 的實際需求；
4. 西洋占星中 `IC` 對星體、虛點與宮位計算是否充分；
5. 凱西占星、榮格占星與其他系統如何共用出生時空及天文基礎資料；
6. 各系統的結構化輸出如何與人生事件、觀察及解釋層連結；
7. timeline／return 的 canonical UTC 與各種顯示 projection；
8. JSON Schema、CLI options 與跨實作測試資料。

完整 SPEC、schema 與 conformance examples 將隨實際程式驗證逐步整理。若實作發現目前代碼無法表達某種必要的時空語意，草案會再修訂，而不是要求真實資料勉強符合既有代碼。

## MIRA-SEES 想帶來的方便

MIRA-SEES 最終希望讓這類對話變得簡單：

```text
「我手上的出生資料是 IB，知道城市與 timezone，但沒有精確座標。」

「這個排盤需要 IC；請補充計算要採用的經緯度。」

「這個事件以 U 保存，顯示時才轉成使用者所在地的行政時間。」

「這份八字結果使用 LSC，並記錄了 EOT 演算法版本。」
```

人不必先讀懂整份資料結構，就能交換一個有清楚邊界的概念；程式也不必猜測那些原本只存在於人類上下文中的假設。

這就是 MIRA-SEES 想建立的共同語言。
